# ADR-0009：以不可变金额分配边扩展 Payment/Invoice 关联

状态：已接受

日期：2026-08-30

## 背景

M1 的 PaymentInvoiceLink 只允许金额与币种完全一致的一笔 Payment 和一张 Invoice 建立全额一对一关系。该模型不能表达一笔支付覆盖多张发票、多笔支付共同覆盖一张发票，或双方只完成部分对账。

M2 首切片需要扩展这些关系，同时继续满足 Source/Claim/Fact、人工审核、整数金额、租户隔离、幂等和并发无部分写入等既有不变量。项目是 Clean Slate，不保留 M1 一对一运行时兼容分支，也不迁移旧数据。

## 决策

1. PaymentInvoiceLink 改为不可变的金额分配边，保存 `payment_id`、`invoice_id`、`allocated_minor`、`currency` 和产生它的接受决定。
2. 同一 Payment/Invoice 对同时最多一条活动 Link；一个 Fact 可通过不同对参与多条 Link，从而表达一对多和多对一。
3. 活动 Link 在任一 Payment 上的分配合计不得超过 `payment.amount_minor`，在任一 Invoice 上的合计不得超过 `invoice.total_minor`。余额只由活动 Link 聚合，不增加可写余额列。
4. 候选硬条件为同租户、相反类型、同币种、业务日期相差不超过 30 天且目标剩余余额为正。金额完全相等只形成排序原因，不再筛除部分分配候选。
5. Review 确认请求使用 `allocate_candidates`、`reject_all` 或 `no_candidate`。分配模式提交唯一候选 ID 与正整数 `allocated_minor` 的非空数组；旧 `accept_candidate + selected_candidate_id` 从活动契约删除。
6. 应用层对完整计划进行规范化排序并计算 SHA-256，ReviewDecision 保存该计划身份。幂等重放必须同时匹配 Claim revision、关联模式和计划身份。
7. 每个候选仍写唯一终态决定。接受决定同时保存分配金额与币种；拒绝决定不保存分配值。每个接受决定产生且只产生一条金额、币种完全相同的 Link。
8. 确认事务重新读取目标 Fact 与活动 Link，验证双方未删除、币种一致、目标余额充足、新 Fact 本次合计不超额，并原子创建 Fact、全部决定、全部 Link、AuditEvent 与 Job 终态。
9. 数据库触发器重复执行币种、删除状态、决定一致性和双方聚合余额约束，以阻止并发或未来写路径绕过应用校验。
10. Link 不原地改写，普通业务写路径也不能物理删除 Link。删除 Fact 终止其全部活动 Link 并恢复另一端的派生余额；独立补分配、撤销和替换工作流不属于首切片。

## 取舍

- 余额查询需要聚合活动 Link，但避免了可写缓存余额与 Link 事实之间的双数据源。
- 一个活动对唯一使审计和并发约束简单；同一对需要改金额时，未来必须以终止旧 Link、创建新决定和新 Link 表达。
- 候选读取的余额只是界面快照；确认事务必须重算，因此并发冲突会明确失败而不是自动缩减用户金额。
- 首切片允许新 Fact 保持部分未分配，但不提供确认后独立编辑关系的入口。
- Link 历史保护触发器会拒绝普通 SQL 物理删除；未来整租户清除必须设计单独的受控机制，在核验租户范围、对象清单和审计要求后显式处理该约束，不能让常规 Repository 绕过历史保护。

## 验证要求

- 领域测试覆盖计划规范化、重复候选、非法金额和新 Fact 合计超额；
- SQLite 集成测试覆盖双方余额、同币种、活动对唯一、删除后余额恢复和并发争用；
- HTTP/OpenAPI/Web 测试覆盖多候选输入、幂等重放、同键改金额、动态余额与可访问错误；
- 关键不变量矩阵必须把 M1 一对一分支替换为 M2 分配与并发超额分支。
