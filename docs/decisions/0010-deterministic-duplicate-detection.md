# ADR-0010：以版本化视觉指纹和字段组合生成重复审核候选

状态：已接受

日期：2026-08-30

## 背景

M1 已有两条精确重复规则：同租户原始 Document SHA-256 完全相同会在上传事务中返回 `duplicate_document`，未删除 Invoice 的规范化发票号码完全相同会产生 `duplicate_invoice_number` blocked ValidationResult。它们不能发现同一页面经重新编码或等比缩放后的近似文件、一个多页文件中的重复页面、不同文件之间的重复页面，也不能提示内容不同但业务字段组合高度一致的 Payment 或 Invoice。

M2 第二切片需要补足这些确定性提示，同时保持 Source/Claim/Fact、人工审核、租户隔离和无第二数据源。重复检测不能由模型给结论，不能自动合并 Source、覆盖 Document、删除页面或直接阻止所有相似版式；下一切片才处理跨页明细续行、重复表头归属和分页重建。

## 决策

### 1. 精确规则保持不变

1. 原始字节 SHA-256 完全相同仍在上传边界硬冲突，不创建第二个 Document 或 Job，也没有人工绕过入口。
2. 未删除 Invoice 的规范化号码完全相同仍为 blocked，不能通过“保留独立记录”绕过数据库唯一约束。
3. 本切片新增的近似、跨页和字段组合判断只产生疑似重复候选，不改变上述精确规则。

### 2. 页面视觉指纹

每个已经由 `document-normalize/2` 生成的 8 位 RGBA PNG 页面额外计算 `page-visual-dedup/1` 指纹，不修改原始 Source，也不产生第二份模型输入：

- 先把透明像素按 alpha 合成到白色背景，再使用 `golang.org/x/image/draw.CatmullRom` 直接缩放到固定采样网格；原始页面宽高比单独参与后续匹配，不靠采样网格保留；
- 每个采样像素使用 8 位整数公式 `(299*R + 587*G + 114*B + 500) / 1000` 得到亮度；
- `dhash64`：采样为 9 × 8 网格，按行优先顺序比较每行相邻像素，左侧亮度大于右侧时对应 bit 为 1，得到 64 位差异哈希；
- `ahash64`：采样为 8 × 8 网格，先以整数和除以 64 得到向下取整平均值，再按行优先顺序把亮度大于等于平均值的 bit 置为 1，得到 64 位平均哈希；
- 指纹均保存为 16 位小写十六进制；`dhash64` 同时拆为四个 16 位检索 band；
- 页面只有在宽高比差异不超过 1%、`dhash64` Hamming 距离不超过 3 且 `ahash64` Hamming 距离不超过 3 时才是视觉近似页。

四个 dHash band 使“距离不超过 3”的页面至少有一个完全相同 band；SQLite 先用同租户、同版本和任一 band 相等检索，再由应用层执行完整宽高比与双哈希判断。阈值、采样、灰度公式、位序或检索 band 变化必须产生新版本并重新验收，不能原地漂移。

本规则只承诺同方向页面的重新编码和等比缩放；旋转、裁切、遮挡、屏摄、低清修复和版面语义相似度不属于本切片，也不得借此重新引入 OCR 或模型预处理补丁。

### 3. 三类候选

重复规则版本固定为 `duplicate-detection/1`：

1. `near_file`：当前 Document 与同租户另一个 Document 页数相同，且按页码一一对应的全部页面均为视觉近似页。每个目标 Document 只产生一个候选，记录两种哈希的最大距离。
2. `cross_page`：当前 Document 内两个不同页码近似，或当前页与另一个 Document 的某页近似，但该目标 Document 未被同一次检测归为 `near_file`。每个确定页面对产生一个候选。
3. `field_combination`：只对本地校验后字段生成。Payment 要求活动目标与当前字段的正数金额、币种、规范化商户完全一致，交易时间相差不超过 5 分钟；双方非空订单号一致只增加原因代码。Invoice 要求活动目标与当前字段的正数价税合计、币种、开票日期、规范化销售方和购买方全部一致，且不重复生成已由精确发票号规则阻断的同号候选。

名称规范化继续使用 Unicode NFKC、首尾空白去除、连续空白折叠和拉丁字母大小写折叠；不增加编辑距离、拼音、模糊文本或模型判断。候选按种类、距离、目标 ID 和页码确定性排序；同一 Claim revision 最多保存 50 个，超过时写入 `duplicate_candidate_limit_exceeded` blocked ValidationResult，不静默截断后继续确认。

### 4. 候选与审核决定

- DuplicateCandidate 是 Claim revision 的不可变审核输入，只保存同租户目标 ID、页面引用、版本、原因代码和距离，不复制原始页面、完整财务字段或模型响应。
- Review API 返回候选类型、可用目标摘要、原因代码、相关页码与距离；目标后来被删除或不可用时明确标记，不把“查不到”解释为其他租户是否存在。
- 存在候选时，用户确认 Fact 必须为当前完整候选集逐项提交唯一的 `keep_distinct` resolution；缺失、重复、伪造、跨租户或其他 revision 的候选全部拒绝。
- 用户判断当前 Document 是重复项时使用既有 Reject 工作流，不创建 Fact；系统不自动合并、删除、覆盖、跳过或把既有 Fact 作为当前结果。
- resolution 规范排序后计算 SHA-256，进入 ReviewDecision 的 `duplicate_plan_hash` 和幂等身份。确认事务写入每个 DuplicateCandidateDecision；数据库在 Claim 转为 `confirmed` 前再次保证当前 Claim 的所有候选都有同一确认决定下的 `keep_distinct` 记录。
- 修订字段会产生新的完整 Claim revision并重新生成三类候选；旧 revision 的候选不能用于确认新 revision。

### 5. 确认时重检

确认事务必须用冻结规则和当前数据库状态重算候选键。候选集合有新增、消失或目标状态变化时返回 `duplicate_candidate_set_stale`，Fact、ReviewDecision、候选 resolution、Link、AuditEvent 和 Job 状态全部不写入；用户保存当前完整字段为新 revision 后重新审核。SQLite 写事务使用 immediate lock，因此两个原先都没有字段重复目标的并发确认最多一个能以原候选集成功，后一个必须看到集合变化或数据库硬冲突。

## 取舍

- 双 64 位视觉指纹是高精度疑似重复筛选，不是图像语义识别；严格阈值会保留一部分漏报，但能避免为普通同版式票据制造大量误报。
- 指纹是可重建页面派生元数据，不是 Source 或 Fact 的第二事实来源；任何正式业务结论仍来自 Claim 与用户决定。
- 候选快照使审核可追溯，确认时重检避免陈旧快照在并发下静默通过；代价是目标集合变化后需要创建一次新 Claim revision。
- 跨页候选只指出重复页面，不拼接明细、不删除重复行，也不判断表头、续行或页序；这些能力保留给下一切片。

## 验证要求

- 纯合成图片覆盖重新编码、等比缩放、明显不同页面、宽高比边界、双哈希阈值和 band 检索完整性；
- SQLite 集成测试覆盖同租户/跨租户、整份近似、同文档重复页、跨文档页、`near_file` 对页面候选的去重、50 项上限和目标删除；
- 领域与事务测试覆盖 Payment/Invoice 字段组合、精确发票号优先、revision 重算、完整 resolution、幂等重放、集合陈旧和并发无部分写入；
- OpenAPI、生成客户端和 Web 测试覆盖候选摘要、逐项 `keep_distinct`、拒绝当前 Claim、键盘操作、文字错误关联及窄屏布局；
- 不调用真实 Provider，不新增 OCR、模型依赖、模糊文本库或外部服务。
