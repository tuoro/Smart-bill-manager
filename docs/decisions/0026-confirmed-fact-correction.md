# ADR-0026：已确认 Fact 的可追溯纠错

状态：已接受，B2 已本地验收；证据见 `tests/evidence/business-completion/b2-fact-correction.json`
日期：2026-09-04

## 范围

按已授权 B1～B6 计划，允许 Owner/Finance 对未删除的 Payment、Invoice、TripEvidence 修正字段。类型与 Fact ID 不变，原件不可变；费用行程容器继续使用 ADR-0024。不重开识别 Job、不调用 Provider、不支持无原件记账，不把 Payment 与 Invoice 互相转换。

## 身份与来源

- 保留 `source_review_decision_id` 作为首次确认身份，原确认幂等回放继续有效。增加 `current_review_decision_id` 指向当前有效字段的确认决定；直接复用 ReviewDecision 身份作为字段修订身份，不再创造平行的字段 JSON 或独立可编辑版本仓库。
- 新增不可变 `fact_corrections`，连接同一 Fact 的前后 ReviewDecision，记录理由、操作者、请求内容 hash、幂等键、期望/结果聚合版本和审计。已有 `version` 继续表示聚合 CAS，不当作纯字段序号，因为归属操作也会递增它。
- 理由、操作者和幂等键复用关联 ReviewDecision，不重复保存；纠错记录的结果版本在自动归属重算后取得，可能大于期望版本加一，并用延迟约束核对最终聚合版本。
- 每次确认纠错生成完整 Claim revision、用户字段/Evidence、Validation 和显式 ReviewDecision；旧 confirmed Claim 和旧 ReviewDecision 保持不变，Job 保持 completed。Claim revision 继承真实 AI/人工根来源；可信纠错用例允许人工标注原件，不通过清空真实 AiRun 身份获得该能力。
- 发票明细按 ReviewDecision 作用域保存；旧明细行、ID 与字段来源不删除。`fact_field_origins` 唯一约束扩展到 ReviewDecision 作用域。列表、洞察及当前报销只查询当前投影/明细；历史通过原 Claim 和来源链读取。
- 前向迁移 `0004` 为既有 Fact/明细建立首次确认指针，保持既有业务字段、ID、聚合版本、关系和历史。数据库保护要求字段更新对应同租户、同类型、同原件、用户确认的纠错决定；不能仅删除 TripEvidence 的不可变保护。

## 工作流与失败边界

1. 读取纠错工作区：当前完整字段与来源、聚合版本、字段修订身份、全部活动分配和当前归属，以及可查询的历史。要求同时具有 `facts.read` 与 `claims.review`，不允许 Reviewer 通过该入口管理正式账单。
2. 用户编辑完整字段、人工证据和 1～500 字理由，显式选择本次撤销的活动分配。预览复用既有字段校验/Fact 构造与重复检测，返回新旧值、保留/撤销分配、自动归属影响、重复候选及内容绑定的预览 hash；预览不保存草稿、不创建 Claim/Fact。
3. 用户逐项确认重复提示后提交同一预览。事务重新读取并验证完整内容、Fact 聚合版本、当前修订、全部相关关系/目标与重复候选；变化即冲突，不能自动接受新关系。
4. 同一事务结束明确选中的旧 Link、创建纠错 Claim/Review 与历史记录、更新同 ID 当前投影、写字段来源并重算适用自动归属。失败无部分结果。相同幂等键及相同内容回放同一纠错；不同内容复用键冲突。

### 关联规则

- 所有活动分配都进入预览，不能把 30 日候选查询当作活动关系全集。保留链接必须仍满足同币种与双方余额；日期硬限制已由 ADR-0031 取消；冲突显示具体原因，用户可以明确撤销相关链接后纠错。不得静默减额、删除历史 Link 或自动清空分配。
- 本次纠错只保留或撤销已有 Link；添加或替换分配金额继续使用已存在的独立分配工作区。用户可先调整分配再重新预览纠错，或纠错并明确撤销后补充分配；不在纠错表单复制第二套候选/金额编辑器。纠错及其选定撤销必须原子提交。
- Payment 时间/时区更正后复用唯一自动归属实现，保留人工归属及禁止自动偏好；预览说明变化。Invoice 不新增自动归属。TripEvidence 更正不更改费用容器日期、不自动移动已有材料关联。
- 规范化发票号冲突（排除自身）仍阻断；模糊重复保留既有检索/阈值/50 项边界，用户逐项确认，事务重验，不能让自身成为重复候选。

### 报销历史

- 新报销项记录当前 ReviewDecision 修订身份，纳入预检 hash；纠错使此前预检失效。已提交、已报销和已驳回快照的字段、状态历史、hash 均保持不变。
- 前向迁移不重新计算旧报销 hash，也不把当前修订冒充旧快照来源；旧项未记录修订身份时明确标为“历史快照”。重复使用提示继续按稳定 Fact ID，不按新修订身份绕过。

### API/UI 边界

- 工作区和历史使用 `/api/v1/facts/{fact_type}/{fact_id}/correction` 与 `/history`；历史按 Claim revision 倒序 keyset 读取，不能固定截断为完整历史。
- `/correction/preview` 接收当前 Fact 聚合版本、当前 ReviewDecision、完整固定类型字段、理由和撤销 Link 清单；返回校验/分配冲突、归属影响与稳定重复候选 key，不写数据库。
- `/correction` 的 POST 确认接收相同内容、预览 hash 和逐项确认的重复 key，要求 CSRF 及 Idempotency-Key。客户端不得传新的内部 Claim、Fact、ReviewDecision 身份或来源用户。
- 支付、发票及行程凭证提供最小纠错入口；界面展示当前字段、原件与历史，编辑后先预览、比较并明确确认，失败保留草稿，409 必须刷新并重新核对。新增/替换分配金额链接到既有工作区。

## 本地验收

- 三类 Fact 的首次/多次纠错、旧确认回放、当前字段和逐版历史/原件来源，完整发票明细增删与旧明细来源保留。
- 未分配与已分配；合法及跨期链接保留、降额/改币种冲突、明确撤销、并发关系变化与事务注入失败回滚。
- 人工归属优先；Payment 日期变更引起的唯一匹配/重叠/无匹配可解释；TripEvidence 材料归属不意外移动。
- 三种报销状态保持原快照；新预检绑定新修订、旧预检冲突，同 Fact 重复使用提示不丢失。
- 并发纠错、同键回放/冲突、原件/证据/租户/角色边界、重复候选变化与发票号冲突。
- `0004` 故障与正常前向升级、认证恢复；领域/数据库/HTTP/OpenAPI/Web、最小管理入口和浏览器完整操作，适用覆盖率、静态检查及构建通过。

只有安全聚合证据完成后收口 B2。仅使用重新创建的 owner-only 合成测试环境，重型验证串行；不修改用户实例、不下载、不提交或发布。
