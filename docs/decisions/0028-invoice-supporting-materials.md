# ADR-0028：发票辅助材料与报销材料快照

状态：已接受，B4 已通过本地验收；证据见 `tests/evidence/business-completion/b4-invoice-materials.json`
日期：2026-09-04

## 范围与权限

给已确认发票上传或关联图片/PDF，查看、下载、解除关联。复用不可变 `Document` 和当前本地对象存储；辅助用途由关系表达，不新建文件数据源，不产生识别 Job、AiRun、Claim 或 Fact，不修改发票字段。已有 Document 可被多张同租户发票共享；本发票原件不得再作为自己的辅助材料。

管理、候选与材料读取要求 `facts.read`、`review.source.read`、`documents.process`，即现有 Owner/Finance。Viewer 不收到辅助原件标识、文件名或地址；Reviewer 不因有上传权限获得已确认发票管理权。现有原件端点接通无 Job Document，Reviewer 的待审核来源限制不变。图片与 PDF 直接打开不可变原件，不额外渲染页面或调用模型。

## API 与交互

- `GET /invoices/{invoice_id}/materials` 返回当前 Invoice 聚合版本和全部活动材料，每张发票最多 100 份，超限明确拒绝，不静默截断。
- `GET /invoices/{invoice_id}/material-candidates` 按不可变 Document 入库时间/ID keyset 分页；`q` 为规范化文件名字面子串，`limit` 默认 20、范围 1～100，`cursor` 绑定租户、发票和筛选。排除本发票原件及已活动关联；不从固定前 200 个 Job 拼出候选。
- `POST /invoices/{invoice_id}/materials` 显式关联 `document_id`；`POST /invoices/{invoice_id}/materials/upload` 只接受一个文件与版本/理由/幂等字段；`POST /invoices/{invoice_id}/materials/{link_id}/remove` 解除当前关联。
- 每次写入需要 `expected_version`、非空 `reason` 和 `idempotency_key`；参数封闭、重复/未知参数拒绝。相同请求幂等回放，不同请求复用键冲突；不同键重复添加活动材料冲突。解除后重加产生新 Link，不覆盖旧决定。
- 发票详情显示独立“辅助材料”区，不混入票面原件或发票明细。支持单文件选择、已有材料分页选择、明确移除确认、预览与下载；保存时禁止重复点击。失败保留输入，409 必须刷新并重新核对版本，不能自动重试写入或静默重新关联。

## 事务与数据模型

前向 `0006` 新增 `invoice_material_links`、`invoice_material_decisions`、`reimbursement_material_snapshots` 与报销捕获标记；保留已发布 PostgreSQL 数据，不改既有迁移。租户复合 FK、活动 `(invoice_id, document_id)` 唯一、决定/快照不可变，Link 只能一次性终止。

材料写入用 ReadCommitted 事务，在数据库先锁 Invoice、再锁 Document，核验聚合版本后原子写 Link/决定/Audit 并增加 Invoice.version。文件 SHA 仍以 `(tenant_id, sha256)` 唯一；相同 SHA 复用原 Document 的身份、名称、内容类型与对象 key，不复制共享原件。发票软删除与写入共享 Invoice 行锁，并终止材料 Link；删除 Audit 与材料历史保留。

## 文件发布、失败与恢复

文件准备复用原上传的规范文件名、Stage、Inspect 与既有 20 MiB、20 页、类型/MIME/签名边界。新辅助 Document 不创建 Job，只有完整原件发布和关系事务完成后才返回成功。关联已有 Document 也要确认其原件可读取，普通上传尚未发布文件的窗口不能生成成功材料关系。

PostgreSQL 与文件系统不能组成单一事务。只为本次新随机对象建立 owner-only 持久化发布意图，记录发布 ID、租户、新 Document 身份、staging 身份、精确 key 和哈希，不保存文件内容、名称、凭据或第二份业务关系：

1. 材料事务先取得发布 ID 对应的 PostgreSQL 事务锁，再原子持久化意图并发布对象，然后 SHA 去重和写入材料关系。锁在整个提交期间保持。
2. 成功或错误后通过独立 ReadCommitted 事务取得同一发布锁，再核对新 Document 的精确身份。等待锁释放后再执行查询，不能用等待之前的快照或单次“暂时查不到”推断原事务已回滚。
3. 新 Document 已提交则保留其对象；未采用本次随机 key 则仅删除本次对象和暂存文件。不得删除去重命中的共享对象。清理完成后移除意图。
4. 原进程中断或结果无法确认时保留意图，返回明确失败；启动时逐项恢复核对，未完成不得启动业务服务。损坏/未知意图、对象不一致及补偿失败必须暴露，不盲删、不伪成功。

这只是本次发布的精确恢复，不增加全库 GC。离线备份发现未收口发布意图应要求先完成恢复，不能放宽对象精确集合检查。所有文件处理有界，不将完整材料集合载入内存。

物理删除的预案、最终事务与普通上传失败补偿同时检查材料历史引用；最终删除和关联共享 Document 锁。预案后新增关联导致删除失败时，沿用既有可恢复隔离区恢复原件。移除仅终止 Link，曾被材料历史或报销引用的 Document 保留；邮件拥有的对象所有权不变。

## 报销材料固定与历史

报销预检把本次所选 Invoice 的活动材料 Link/Document 身份纳入确定性哈希；不沿支付分配关系扩展到用户未选择的发票。移除再重加通过新 Link ID 检出 ABA。提交在同一个 Serializable 事务重读、比较并写不可变材料快照；与材料变更并发可排序为任一先后，但不得提交混合版本。

新报销 `materials_captured=true`，即使集合为空也明确捕获；不可变 `material_count` 与提交时精确子表行数以延迟约束一致核对，不能在提交后追加材料。前向升级只给历史报销标记 `false`、计数为 null，不补入当前附件、不改历史 hash 或状态决定。当前政策快照版本递增，历史版本保留为历史数据，不引入双运行链。报销详情向读取者提供捕获状态，只有同时具备辅助材料读取权限才提供计数，否则为 null；不因仅有 `reimbursements.read` 而泄露文件身份或来源。B6 再提供获授权的固定快照材料交付入口，历史未捕获状态必须明示。

全部对象仍由 Document 引用，精确备份对象 UNION 不新增第二分支；新历史表进入恢复稳定清单。辅助材料变更和发票纠错不得改写已提交、报销、驳回的材料快照。

## 验收与退出

- 无模型上传合法图片/PDF、多个辅助材料、同 SHA 共享、重复关联/幂等、解除重加、四角色/租户与原件区分。
- 签名/大小/损坏拒绝，发布或事务失败回滚，去重后只清理新对象；中断恢复与提交未确定时等待同一发布锁，不能遗失共享文件或留下无效关系。
- 关联与原件删除竞争、发票软删除、旧删除预案的原件恢复；材料历史保留且不可改写。
- 材料增删使旧报销预检失效，三态快照/来源保留，历史报销不回填；选择范围与跨租户边界明确。
- 真实 PostgreSQL 17 的 `0006` 前向/重复升级、故障回滚，以及非空辅助材料、共享对象、解除后历史报销的认证 dump/restore，精确对象检查不放宽。
- HTTP/OpenAPI/Web 上传、候选翻页、移除、失败和权限操作通过；适用 Go/Web 全回归、覆盖率、构建、浏览器与响应式通过后才记录聚合证据。

不包含新依赖、模型正确率、真实联调、提交、发布或用户实例升级。重型门禁串行，临时资源按阶段回收。
