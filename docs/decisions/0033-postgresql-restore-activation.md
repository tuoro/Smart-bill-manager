# ADR-0033：PostgreSQL 恢复激活的唯一状态与对象配对

状态：已实施并通过本地验收
日期：2026-09-05

## 目的与范围

修复 v0.4.0 发布复核发现的恢复中断窗口：数据库已恢复、旧会话尚未失效，或对象/密钥只发布了一部分时，所有运行入口都必须拒绝使用该副本。保持 ADR-0020 的 PostgreSQL 唯一关系数据源、全新恢复目标、停写/RPO 0、精确对象和前向升级边界；不新增业务功能、不读取 SQLite、不清空已发布版本的数据。

## 决策

- 恢复状态只存同一 PostgreSQL 数据库的操作 Schema `sbm_restore`，不复制业务字段。`state` 固定一行，包含格式版本、随机恢复身份、数据库 OID/名称和 `incomplete` / `complete`。该操作状态不属于业务 `public` Schema 或领域迁移，不进入 pg_dump；每次全新恢复创建自己的状态，不能复制上次 complete。
- 在任何 dump 写入前，在迁移使用的同一个事务 advisory lock 内重新核实目标没有用户 Schema/对象，并提交 durable incomplete。普通 migration 在取得同一个锁之后也检查该状态，不能越过它。数据库不是空目标、已有恢复状态或出现并发迁移均显式失败；不覆盖或自动重试既有目标。
- 普通 PostgreSQL `Open` 统一拒绝 incomplete、未知、损坏、空行/多行及数据库身份不匹配。恢复命令只通过本轮创建的专用控制器检查并处理未激活副本；不提供配置开关、环境变量或命令行绕过。
- 状态创建事务提交后即释放 advisory lock，不需恢复全程持锁。普通 migration 使用 READ COMMITTED，在锁内读取最新状态并拒绝 incomplete；完整迁移集合已在 dump 中，恢复控制器只精确核对并授予 public 运行权限，不重新执行普通迁移器。`Open` 在迁移检查之后最终读取恢复状态，避免先见空库、等待恢复提交后的时间窗口。
- 新对象树含一个 owner-only `restore-identity.json`，只存配对身份、不存第二份完成状态。server、bootstrap-owner、recover-account 及备份入口在创建对象目录或执行业务写入前，用共享校验核对对象身份。恢复库缺文件、文件损坏/链接/权限错误、其他库文件、普通库出现孤立文件均拒绝。
- 从未执行恢复的普通安装/前向升级库没有 `sbm_restore`，也不应有对象配对文件；这是正常生命周期，不是旧数据库兼容分支。其业务 Schema 和数据升级方式不变。
- 所有入口要求对象根已经由部署准备器建立且路径为真实目录；配对检查不自动创建缺失根，也不声称检查普通库每个业务文件的完整性。
- 恢复命令依次校验原快照、失效 Session/未消费邀请、设置租约宽限、再次校验；在对象与独立主密钥均发布、文件/父目录同步和后检查完成后，最后以一笔 PostgreSQL 事务将唯一状态改为 complete。此前任一错误均保留 incomplete。失败目标不自动修复、合并或删除；操作者保留它用于诊断并选择新的空目标重新恢复。
- 完整恢复后的再次备份校验当前配对，但 dump 固定排除 `sbm_restore`，对象包仍只含精确的业务 `objects/`，不含旧配对文件；再次恢复生成新身份。
- `backup verify` 的包认证/文件核对与 scratch 数据库语义恢复分开描述。独立验证必须额外在一次性空目标执行完整 restore，再销毁验证副本，不能把 dump 目录检查当成语义恢复。

## 验收与失败边界

1. 确定性注入 dump 已提交、会话失效前的失败：旧 Session 仍可存在于离线副本，但运行入口必须在认证或写入之前拒绝打开副本。
2. 确定性注入对象已发布、密钥发布失败；以及激活前失败：命令报错且状态保持 incomplete，不能因对象目录存在而启动。
3. 正常完整恢复可以打开，旧 Session 失效、原数据与对象保持；配对文件缺失、损坏、被替换及数据库身份错误均拒绝。合法的空身份快照不能借 bootstrap-owner 绕过 guard。
4. 并发恢复/普通 migration 不得提前打开状态；runtime 只能读取操作状态，不能创建、修改、删除或激活它。普通安装与前向 migration 继续通过。
5. 完整恢复后再次备份/恢复可成功，业务迁移、约束、审计和精确对象边界不放宽。
6. 证据工具必须消费与当前构建身份一致的实际故障注入报告，不再固定输出通过字段。历史报告不改写，未验证项仍为未通过。
7. 修复后重新构建候选，完成 v0.4.0 冻结门禁。只使用新 owner-only `/tmp` 的一次性 synthetic 资源与已有镜像；重型工作串行且及时清理，不升级用户实例。

`tools/write-restore-activation-evidence.mjs` 直接运行隔离 PostgreSQL 测试，不接受外部成功日志：执行前后核对 HEAD、发布输入摘要与候选镜像标签，强制 `-count=1`，实际 server/账号入口只取该候选的 `/app`。全部具名故障/对照用例必须执行成功，缓存、缺失、跳过和失败均拒绝。1,000 Document 的执行控制器另将每步已核验 image ID 与原始结果摘要绑定；合并器要求其与 activation/static 的候选一致，不能把旧大演练贴为新候选通过。

2026-09-05，最终候选实际入口的 9 项故障/正常对照、1,000 Document 认证备份与独立 scratch 恢复、会话失效及 Worker 恰好一次续跑均通过；完整门禁与候选身份见 [v0.4.0 发布记录](../releases/v0.4.0.md) 和 [恢复聚合证据](../../tests/evidence/m4/v0.4.0-backup-restore-gate-summary.json)。历史固定通过字段不作为本次依据。

## 不采用的方案

这是受支持当前镜像入口的应用级保护；全新离线目标只能由与备份迁移集合匹配的镜像接管，不授权旧二进制或任意 SQL 客户端使用恢复副本。数据库管理员主动改写状态/撤销存储权限不属于崩溃恢复模型。

不新增全局账号状态、双写状态文件、运行时恢复绕过开关或兼容入口。仅撤销 CONNECT 不足以处理既有连接和同数据库角色继承；文件 marker 单独存在也不能在挂错对象目录时阻止读取已恢复数据库。采用数据库唯一状态加无状态对象身份配对，而不是两套独立状态机。
