# ADR-0034：连续审核与明确的单次确认

状态：已完成本地 Web 验收，未提交或发布
日期：2026-09-05

## 目标与范围

在 v0.4.0 现有识别、校验与人工 Review 链上减少机械操作。首切片只改 Web 收件箱、审核工作台及其测试；不改变 AI/Provider 契约、HTTP 请求协议、Fact 创建权限、领域规则或 PostgreSQL Schema，不升级运行实例或自动发布。

正常单据核对后只需一次明确的最终保存确认；连续审核让用户不必每张返回收件箱。它不是自动入账或批量确认，校验通过也不代表票面识别正确。

## 交互与唯一数据源

1. 具备 `claims.review` 的用户可从收件箱明确开启连续审核。队列只冻结当前已加载、当前筛选内 `needs_review` / `blocked` 的任务 ID 和显示顺序，最多 200 项；不枚举未加载任务、不轮询追加、不创建 Batch 数据库实体。单项原有审核链接继续用于单独审核。
2. 队列仅为当前浏览器页签内存工作集，绑定当前用户和租户；不保存 Claim、字段、证据或凭据，不写 local/session storage。退出登录清空，身份/权限不匹配不可继续；整页刷新后明确提示队列不再保留，当前单据仍可单独审核。返回收件箱可继续未结束队列或明确结束它。
3. 每次进入任务从现有 API 读取最新 Review。只有当前任务的确认/驳回收到成功结果才推进，下一项绝不自动提交。用户也可明确“稍后处理”，仅计入暂缓数，不改 Job、不算审核成功。已结束/失去访问权的任务不自动跳过，显示当前错误后由用户暂缓或结束队列。
4. 无关联候选的 Payment/Invoice 不再提供“确认当前没有候选”单选；页面和主按钮明确表达“确认保存，不分配”。这一次点击同时授权保存及 `association_mode=no_candidate, allocations=[]`，不是隐藏默认关联。有候选时仍须明确分配或拒绝全部；TripEvidence 仍不发送金额分配字段。服务端原有候选、余额和 revision 重校验不变。
5. 所有字段、原件、页码和证据保留。校验异常/警告始终展开，通过项可折叠查看；异常可定位对应字段与证据。没有异常只表述“规则校验未发现问题，请核对原件”，不展示模型置信度或承诺正确。疑似重复仍逐项决定，必需字段/证据缺失和金额冲突仍阻止确认。
6. 同组件切换任务必须清空前一单的字段草稿、页码、选中证据、关联决定、驳回理由、错误和完成态；取消过时读取并拒绝迟到读写响应覆盖新任务。成功继续后焦点转到新单据标题，并播报上一项的明确结果。
7. 修订草稿未保存时，继续/暂缓/驳回不可丢弃草稿；先保存或明确放弃。离开页面提示未保存变化。提交期间禁止重复提交、修改字段/证据和用户切换任务；认证失效导航不被阻挡。提交 409 保留当前任务并要求刷新核对；结果未知时保留原请求及幂等键，只能显式重试同一决定，不自动跳过或换计划重提。

## 验收协议

- 以源码 `32afe1e3dc6dcadcbff0ad69f482942436ccdd27` 为旧交互基线。固定 20 份无异常合成单据与固定候选结果：从收件箱开始，到最后一份保存成功；实际浏览器记录任务间导航、无候选机械确认和最终保存的点击数，核对恰好 20 次正确确认请求。
- 新旧使用相同合成任务和输出，不调用真实模型。先实测旧基线，再测新流程；不把设计计算、脚本运行时长或合成结果冒充用户时间节省/模型正确率。真实主动操作时间、字段修订率和 30% 减负目标仍待授权后的用户场景测量。
- 正常单独审核只需一个最终确认；连续队列不需要返回收件箱，20 次正式决定不可减少。候选分配、重复、blocked、多页原件、人工来源、驳回和暂缓有独立行为验证。
- 覆盖提交失败不推进、未知结果同键重试、409 刷新、下项读取失败可重试、任务切换/迟到响应、草稿与选择不串单、队列不混入新任务、权限/会话切换及刷新退化提示。
- 沿用 384/768/1024/1440、浅深主题、键盘/焦点、对比度与无横向溢出标准。通过项展开后仍能查看，异常必须可达；不以收起异常减少点击统计。
- Web 单元、契约生成、类型、lint、格式、构建及受影响 Mock 浏览器回归通过；纯静态预览不代理任何 API，未声明 API mock 请求明确失败。真实后端/Provider 代表测试只同步新交互断言，本次不冒称已运行。
- 重型工作串行，浏览器单 Worker，全部输出只进本轮 owner-only `/tmp`；阶段前后检查内存，不新下载依赖、不读取用户真实数据。最终审查 diff、敏感信息和临时资源，保留安全聚合证据。

## 本地验收结果

安全聚合与已验收文件 SHA-256 见 [`continuous-review.json`](../../tests/evidence/review-reduction/continuous-review.json)。旧基线先于生产代码修改完成，新旧共享 `apps/web/e2e/review-reduction-fixtures.ts` 的固定 10 张支付、10 张发票；均为纯合成、固定识别结果、无异常且无关联候选。

| 实际浏览器操作 | v0.4.0 基线 | 连续审核 |
| --- | ---: | ---: |
| 进入单据及任务间导航 | 39（20 次进入、19 次返回） | 1（开启本轮） |
| 无候选机械单选 | 20 | 0 |
| 明确的最终保存 | 20 | 20 |
| 合计 | 79 | 21 |

固定流程减少 58 次点击（73.42%），两边均核对恰好 20 个正确任务、完整请求体与独立幂等键，未声明请求和页面异常均为 0。点击数不包含原件核对、滚动、字段修订和人的主动操作时长；不能推导真实用户节省 73.42% 时间，也不能证明 AI 识别正确率或原定 30% 时间减负目标。

- 契约生成无差异，类型、lint、格式、生产构建通过；12 个单元测试文件、56 项测试通过。
- 最终生产构建的 15 个 Mock 浏览器测试文件共 136 项通过，0 失败/跳过/重试，含新增 20 项连续审核行为测试。真实后端/Provider 代表流程只更新按钮断言，未运行。
- 新异常工作台覆盖四档宽度、浅深主题、无根横向溢出、操作按钮文字对比度至少 4.5:1；通过规则键盘展开、换单标题焦点、异常定位及截图检查通过。
- 复核发现并修复了修订中直接驳回会丢弃草稿、修订提交中仍可改证据两个边界；新增悬挂请求与草稿回归。旧读取用请求取消和回调结束后断言验证，原件以新文档的图片 URL 和原件链接直接核对。

## 复测入口与边界

新流程入口为 `apps/web/e2e/review-reduction.spec.ts`；其中 20 单用例在成功执行每次 `click()` 后计数，并把聚合结果附为 `interaction-counts.json`。在仅绑定 loopback、明确关闭 API 代理且未 Mock 的 `/api` 返回 501 的静态生产预览上，于 `apps/web` 目录使用现有依赖执行：

```sh
review_check_dir=$(mktemp -d /tmp/sbm-review-check.XXXXXX)
SBM_E2E_BASE_URL=http://127.0.0.1:18085 \
SBM_E2E_OUTPUT_DIR="$review_check_dir/playwright" \
npm run test:e2e -- e2e/review-reduction.spec.ts --workers=1
```

旧基线需从上述固定源码身份单独构建静态 UI，并复用同一 fixture：逐张点击收件箱“审核”→“确认当前没有候选”→“确认并保存记录”，仅前 19 张完成后返回收件箱；校验 20 个顺序正确、revision 及无分配请求体正确的确认和 20 个独立幂等键。不要在当前用户实例上重演，不要使用会代理真实 API 的默认预览配置，不要混跑 `m1-representative-flows.spec.ts`。

原始浏览器报告、截图和旧构建仅保留在本轮私有临时目录，交付时清理；仓库只保留纯合成测试和安全聚合，不保存单据原图、真实字段或凭据。
