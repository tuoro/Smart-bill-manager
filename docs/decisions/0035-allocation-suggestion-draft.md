# ADR-0035：已确认支付与发票的分配草案

状态：已完成本地 Web 验收，未提交或发布
日期：2026-09-06

## 目标与现有缺口

用户已同意推进审核减负后的第二切片：系统利用已有识别结果和关联候选准备可修改的配对与金额草案，显示依据、剩余和疑点，最终明确确认后才保存。此次只在已确认 Payment/Invoice 的“调整分配”页实现；行程整理、新模型、真实质量/时间评测、发布和实例升级不在范围内。

现有工作区已提供当前 Link、同币种 30 天候选及金额/名称/日期提示，但新目标仍须逐项勾选、输入金额。`GetAllocationWorkspace` 在同一只读 Repeatable Read 快照读取当前事实与余额，可直接支持界面草案；初次 Review 候选的部分匹配元数据来自生成时快照，本次不改变该入口，不建立第二套关联候选或模型链。

## 建议边界

1. 草案只是 Web 派生的、未保存的输入建议；不新增 API、Schema、数据库实体或持久化缓存，不写 local/session storage。只有“采用到编辑区”才修改本页草稿，展示建议本身不勾选、不填写、不提交。
2. 仅以本次完整初始工作区准备建议：默认 30 天、未做搜索/翻页、`next_cursor` 为空。首屏不完整或用户搜索后明确说明范围不足，保留手工搜索/分配；不遍历全量候选，不把最后一页当成完整集合。刷新工作区后重新计算。
3. 保留全部当前活动 Link 的目标与金额，包括窗口外已有关系。建议只追加没有当前 Link 的目标，不建议增加既有关联金额、撤销或替换；完整计划仍最多 200 项。
4. 建议目标必须为相反类型、同币种、名称一致、日期差 0～30 天、余额为正且金额可用安全整数表达。名称匹配沿用服务端快照的 `name_exact`，不在 Web 重新规范化名称或排序打分。按 ID 展示只是稳定顺序，不代表推荐优先级。
5. 只有一个同名目标且其剩余金额等于锚点剩余时，准备等额草案；多个同名新目标的剩余金额合计恰好等于锚点剩余时，准备每个目标按其余额分配的待核对组合。合计不等时显示多种可能，不能贪心填满、求子集凑数或挑首行代用户决定。
6. 只有一个同名目标但双方剩余不等时，仅准备目标、金额留空，展示双方余额及本次上限，由用户填写本次实际分配金额。余额是容量，不是本次应付/应分配金额；不假装已经结清或证明一对多关系。
7. 每条建议展示名称一致、日期差、双方余额、建议金额（或待填写）、预计剩余及明确提醒：同名、日期接近、金额吻合不能证明同一交易，必须核对。匹配依据是读取时快照；`plan_hash` 只锁定活动 Link 集合，不承诺名称、日期或全部余额在提交时未变。
8. 用户可不采用，或采用后在原编辑区修改/取消。不得覆盖已有手工目标或金额；已有调整理由原样保留，禁止自动代写业务理由。草案不是第二个编辑器，最终完整计划由既有 rows 与唯一 `validateAllocationDraft` 构建。
9. 刷新、换单、会话变化与 409 冲突使旧建议失效；冲突仍保留当前编辑供核对，刷新/离开前提示未保存变化。提交期间冻结输入、刷新与导航（会话失效除外）。结果未知时仅允许同请求同键显式重试，不允许先换草案再重提；成功后仍从服务端重读当前计划，不伪称刷新失败是未保存。

## 实施与验证

- 单一纯函数生成建议，单一展示组件接入现有 `AllocationPage`。不修改 AI、Review 初次关联、服务端资格/余额规则、跨期手工能力或 Link 不可变历史。
- 先在当前包含 ADR-0034 的未提交 Web 上构建隔离基线，固定 8 个合成场景：两侧等额、一对多组合、保留旧关系的补充分配、部分金额待填、竞争候选和无同名候选。新旧使用同一输入和相同预期完整计划。
- 实际浏览器分别记录目标选择/采用、金额填写、理由填写、最终保存及查询操作。确认请求和完整计划须逐项相等，歧义场景不能靠默认选择减少操作。只宣称所测操作变化，不把脚本耗时或纯合成结果当作用户时间/模型正确率。
- 单元覆盖单个/多个等额、部分金额留空、歧义/无候选、已有关联保留、不完整/搜索范围、200 项边界、安全整数、币种和日期边界，以及不修改输入。
- 浏览器覆盖采用前零写入、修改/不采用、必填理由、既有关联不丢失、分页/搜索/刷新失效、跨期原手工流程、409、未知结果同键重试、提交中输入冻结、迟到响应与会话切换。
- Web 契约生成、类型、lint、格式、单元和生产构建通过；受影响 Mock 浏览器回归使用现有 Chromium、单 Worker、四档宽度与浅深主题、键盘/焦点、无横向溢出和 4.5:1 操作按钮文字对比度。服务端未变，不冒称本次重跑了后端集成或真实 Provider 流程。
- 重型工作串行，先后检查内存；预览仅 loopback 静态内容、无 API 代理，未声明 API Mock 明确失败。原始产物只进入本轮私有临时目录，交付保留安全聚合、清理临时资源；不提交或远端发布。

## 验收结果

2026-09-06 完成本地切片，安全聚合见 [分配草案证据](../../tests/evidence/allocation-suggestion/allocation-draft.json)。只增加 Web 建议纯函数与展示组件，采用仍写入原 rows，由唯一完整计划校验器与显式保存提交；没有后端、API 或数据库改动。

- 同一批 8 个合成场景，实际表单操作从 40 次降到 27 次，减少 13 次（32.5%）。目标勾选 12→2、采用 0→6、金额填写 12→3；理由填写和最终保存均保持各 8 次。两侧的 8 个完整计划逐项相等，已有 Link 的目标与金额保留。
- 部分金额场景仍由人填写 4000，而非默认填到 10000 上限；竞争候选不代选，仍由人选择并填写 5000。每次填写操作按一次 `fill` 计数，不是键击数，也不计阅读、导航、滚动或真实用户耗时。
- 115 项 Web 单元、16 份规格中的 150 项 Mock 浏览器测试全部通过；契约生成无差异，类型、lint、格式与生产构建通过。新增 14 项浏览器覆盖采用、手工保护、范围失效、409、未知结果同键重试、提交冻结、迟到响应、成功后读取失败等路径。
- 采用前/后的 16 张截图覆盖 384/768/1024/1440 与浅深主题，键盘采用与焦点、无横向溢出、采用/不采用/保存按钮普通与悬停状态文字 4.5:1 对比度通过，并完成移动端与桌面端目视复核。
- 首轮暴露的部分金额空值无法触发字段校验已修正；迟到读取测试补齐响应完成屏障，修正页面标题选择器及 Mock 分页字段。首次失败聚合保留，之后局部与全量复跑通过。

本次只证明所测合成表单操作量下降；真实模型正确率、用户核对时间、总体场景收益与 30% 时间减负目标仍未验证。前一切片改动和历史证据保留，未调用真实模型、未升级实例、未提交或远端发布。
