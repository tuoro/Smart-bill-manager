# ADR-0038：支付金额的前导方向符号

状态：已实现并本地验证；真实预检结果待补
日期：2026-09-08

## 背景

`m1-real-dev-v6` 的真实预检显示 `model_field_invalid_money_value` 恰好出现 10 次，等于全部支付样本。原因是 `moneyTextPattern` 要求数字部分以 `[0-9]` 开头：

```
"-440.00"  -> 不匹配
"440.00"   -> 匹配
```

微信与支付宝的支出明细把交易方向印成前导负号，10 份支付样本的票面金额**无一例外**都带负号。也就是说管线在最主要的使用场景上解析不了金额——这与模型质量无关，模型把这 10 个金额一字不差抄了下来。

## 决定

`moneyComponents` 在匹配前剥离前导方向符号（ASCII `-` 与 U+2212 `−`），取其绝对值。

冻结清单已经认定这是正确口径：10 份样本的票面 quote 全部带负号，而 `expected_fields.amount_minor` 全部是正整数（`-440.00` → `44000`）。本决定是把清单已有的口径落到代码，不是新增语义。

## 边界

- 只剥离**前导**符号。符号出现在其它位置（`4-40.00`、`440.00-`、`--440.00`）仍按 `invalid_money_value` 阻断，由 `TestMoneyAcceptsALeadingDirectionSignAndRejectsOtherSigns` 固定。
- 数字本身不做任何改动，分组符与小数位处理不变。
- Payment 的 amount 是支付金额，方向由单据类型表达，不进入金额字段。发票不受影响。

## 已知取舍

剥离符号确实改变了字符所表达的值，与「本地转换只改变表示法」的一般原则有张力。接受它的理由是：前导负号在这类票面上是**方向标记**而非数值的一部分，且冻结清单已按此认定期望值。如果后续出现前导负号真正表示负额的单据类型，必须重新评估，而不是扩大本规则的适用范围。
