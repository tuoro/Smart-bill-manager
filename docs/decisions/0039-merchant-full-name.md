# ADR-0039：支付单据的商户全称字段

状态：实施中
日期：2026-09-08

## 背景

真实预检中 `V5-WECHAT-001/002/003` 的 `merchant` 三轮稳定失败，另有 `ALIPAY-001`、`ALIPAY-003`、`WECHAT-002` 偶发失败。逐样本诊断显示这不是识别错误：微信与支付宝的支付明细页同时印出商户显示名与商户全称，两者都在票面上、都属于逐字抄录，而 `bill-visible-text-cn/2` 对 `merchant` 的说明只排除了「付款人、页面标题、状态、商品说明」，没有规定两者同时出现时取哪个。模型因此在两个合法候选之间随机选择，表现为同一样本时对时错。

产品负责人判定两个名称都要保留，用途不同：显示名用于在账单列表中一眼辨认是哪一笔；全称用于报销与对账，需要唯一可核。

## 决定

新增 `merchant_full_name` 字段。`merchant` 保持为显示名（现有清单标法不变），`merchant_full_name` 保存票面上更完整的商户名称。

`merchant_full_name` 为可选字段（`Required: false`）：并非所有支付截图都印出全称，强制必填会让缺少全称的单据整份阻断，重演 ADR-0037 之前币种缺失导致 Claim 全阻断的问题。

命名采用「商户全称」而非「法人名称」：票面上出现的不一定是法人登记名称，全称更贴近票面用词。

## 范围内

- `bill-visible-text-cn/2` → `/3`：说明两个名称各取哪个
- `claim-mapper/4` → `/5`：映射新字段并从补充字段的 `known` 集合中排除
- `document-claim/3` → `/4`：版本身份变更，结构不变
- `paymentFieldSpecs` 新增一条可选字符串字段，参与既有的确定性名称规范化
- `payments` 表新增可空列；Payment Fact 构造与读取路径同步
- 审核与详情界面展示该字段
- 评测工具契约常量同步；数据集补标全称期望值

## 范围外

- 抽取 Schema 与 Provider Schema **不变**：`bill-visible-text/2` 只校验根身份，`"payment": {}` 对 payment 对象内部不设约束，模型返回新键无需改 Schema
- 判重规则不变：`merchant_exact` 继续使用显示名，全称不进入判重条件
- 报销快照约束不变：数据库触发器对 `display_name = payment.merchant` 的校验继续以显示名为准
- 发票的销售方/购买方名称不在本切片内

## 已知风险

模型在票面只有一个名称时可能把同一个值同时填进两个字段。清单需要对这种情况给出明确期望，否则指标无法区分「正确地留空」与「错误地复制」。

### 更正（2026-09-08）

本决定最初在 prompt 里写了「不要把同一个值同时抄进两个字段」。核对 V5-ALIPAY-002 时发现该票面确实印了两个相同的名称，模型如实各抄一份，是这条规则在惩罚正确行为。更严重的是它违背了管线分工：模型只抄票面原文，判断「两值相同因而应当去重」属于本地语义决策，不能推给模型。

规则改为：两处名称恰好相同时如实各抄一份，不因相同而留空。是否在本地去重是另一个问题，本切片不做——丢弃一份如实抄录的票面值会改变业务含义，超出「本地转换只改变表示法」的边界。

## 待验证

数据集重标需要逐张核对票面，不能以模型输出直接充当期望值。重标完成前，名称与证据相关指标不代表模型质量。
