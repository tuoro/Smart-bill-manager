# 产品基线

状态：M0、M1、M2、M3 已完成；M4 首、第二切片已完成，第三切片已冻结并待实施
产品名称：Smart Bill Manager
产品形态：自托管优先、架构兼容未来托管服务的 AI 财务单据工作台

## 一句话定位

上传任何财务单据，系统自动理解、校验和关联；只有需要判断的内容交给用户确认，每个正式结论都能追溯到原始证据。

## 要解决的问题

个人和小团队的支付截图、发票、邮件附件与差旅行程分散在不同入口。传统 OCR 只能返回文本，无法可靠回答：

- 这份文件是什么类型；
- 哪些字段可信，哪些字段缺失或冲突；
- 一张发票应关联哪笔支付或哪次行程；
- 某个正式字段来自原始文档的哪一页、哪段证据；
- 谁在什么时候确认或修改了 AI 的判断。

Smart Bill Manager 将这些输入统一为可审核的财务事件，而不是把 AI 当作更高级的 OCR。

## 目标用户

- 希望自托管财务单据的个人用户；
- 需要共同整理支付、发票和差旅材料的小团队；
- 需要自带兼容模型 API、保留数据控制权的技术型用户。

第一阶段不为大型企业会计、税务申报或复杂审批组织设计。

## 核心产品原则

### 1. Source、Claim、Fact 分离

```text
Source -> Claim -> Fact
原始证据 -> AI 候选判断 -> 用户确认的正式数据
```

- Source 在其生命周期内保留原始文档身份和不可变哈希，不能被新上传覆盖。
- AI 按 `bill-visible-text/2` 选择约定支付、发票或行程字段并只抄票面原文与页码；`claim-mapper/4` 在本地确定性组装候选值、Evidence、版本和字段级校验结果。
- Fact 只保存从 Claim 经用户确认的正式 Payment、Invoice 或 Trip。Reimbursement 是这些 confirmed Fact 上的独立人工工作流快照，不是绕过 Claim 创建的新 Fact。

### 2. 只打扰真正需要判断的内容

系统让视觉模型判断文档类型、字段语义和发票逻辑明细分组，但只要求它返回需要的票面文字与页码；本地负责无歧义的金额、日期、时区和数量格式化、完整 Claim 快照、Evidence 页序、重复检测与关联建议，不纠正字符、不计算空白业务值，也不重新做版面语义识别。多页发票只从当前 Claim Evidence 派生逐页审核计划，同一跨页明细保持一个稳定身份。系统不自动入账；M2 允许用户在审核工作台为多个候选明确填写分配金额，任何 Link 仍必须由用户确认。

### 3. 每个结论可解释、可追溯

正式字段必须能定位到原始文档、AI Run、Prompt/Schema 版本、字段证据和审核决定。产品不展示模型自报的数字置信度。

### 4. 自托管不等于降低安全标准

租户隔离、密钥加密、文件鉴权、最小日志、可恢复任务与备份恢复属于产品基础能力，不是部署文档中的可选建议。

### 5. Clean Slate

新系统不读取、不迁移旧数据，也不兼容旧 API、旧数据库或旧任务状态。旧实现只用于理解业务经验，不能约束新架构。

## 产品领域

目标产品包含六个领域：

1. AI 收件箱：上传、处理、失败恢复和审核入口。
2. 支付：支付事实、分类、重复提示和统计维度。
3. 发票：发票事实、明细、重复检测及支付关联。
4. 邮箱来源：邮箱连接、邮件来源和附件归档。
5. 行程与报销：行程事实、单据归属和报销状态。
6. 数据洞察：基于已确认 Fact 的筛选、汇总和解释。

## 首条用户旅程

1. 用户选择一张或多张支付截图、发票图片或 PDF；批量时系统按原选择顺序逐项反馈。
2. 每个合法且非精确重复的文件独立创建不可变 Document 和持久化 Processing Job；单项失败不回滚其他项。
3. 兼容模型返回结构化候选结果与字段证据。
4. 本地 Schema 和确定性规则产生 Validation Results。
5. 用户在审核工作台查看原件、修订字段并确认或拒绝。
6. 系统以幂等事务创建 Payment 或 Invoice Fact。
7. Audit Event 记录完整决策链。

## M2 首条用户旅程

1. 用户审核新的 Payment 或 Invoice，先查看近似文件、重复页面和字段组合疑似重复；
2. 用户认为当前 Document 是重复项时驳回；否则逐项明确“仍保留为独立记录”，系统不自动合并、覆盖或删除；
3. 用户继续查看同币种、日期接近且仍有可分配余额的相反类型 Fact，选择一个或多个候选并填写正整数最小单位分配金额，或明确拒绝全部关联候选；
4. 页面展示重复原因、相关页码、目标摘要、本次分配合计、当前 Fact 剩余金额和每个关联候选的最新可用余额；
5. 服务端在一个事务中重新校验租户、重复候选集合、币种、关联候选状态、双方余额和两类幂等计划；任何冲突都整体失败；
6. 成功后创建 Fact、审核决定、重复候选决定、关联候选决定和不可变 Allocation Link，账单列表展示已分配与剩余金额。

## M2 已确认 Fact 调整旅程

1. 具备财务权限的用户从 Payment 或 Invoice 列表进入“调整分配”，查看当前活动 Link 和同币种、日期接近的相反类型 Fact；
2. 用户以完整期望计划勾选目标并填写正整数最小单位金额：保留项不变、增加项表示补充、取消项表示撤销、改金额或换目标表示替换；
3. 页面展示 anchor 与每个目标的权威余额、当前对金额、可调整上限和提交后的合计；理由必填，撤销全部还需一次显式确认；
4. 服务端在一个事务内校验权限、租户、快照、币种、日期、双方余额、活动对唯一和幂等身份；并发变化明确失败，不自动缩减或部分执行；
5. 成功后未变化 Link 保持不动，旧 Link 只终止一次，新关系创建新的不可变 Link；Adjustment 和安全 AuditEvent 保留这次人工决定，列表余额从活动 Link 重新聚合。

## M3 邮箱 Source 首条旅程

1. Owner 注册不含任何凭据的邮箱 Source 描述符；系统明确显示“待连接”，不把保存本地元数据伪装成外部连接成功；
2. 未来邮箱连接器只把一封邮件的稳定不可逆外部键、接收时间和原始 RFC 822 字节提交给内部归档端口；当前本地验收只使用纯合成输入；
3. 系统不可变保存原始邮件与逐附件 Source，显示主题、发件人、时间和逐项安全状态，但不解析或渲染邮件正文；
4. 合法 JPEG、PNG、WebP 或 PDF 附件复用现有 Document/ProcessingJob；精确重复链接已有 Document，其他附件只归档并说明原因；
5. 用户从邮箱来源页进入已有 Document 的收件箱/审核链，后续 Fact 仍只能由 Claim 经过人工 Review 产生。

## M3 行程归属旅程

1. 用户上传清晰的行程单、预订单或票据图片/PDF，模型只抄目的地、起止日期及可见辅助字段，本地确定性规范化并形成 Trip Claim；
2. 用户在既有审核工作台核对证据、修订并确认后，系统才创建正式 Trip Fact；
3. 行程页对已确认 Payment/Invoice 按业务日期和既有支付—发票 Link 给出可解释建议，同时保留全部 Fact 的分页入口；
4. Owner/Finance 为单个 Fact 填写理由并显式分配、移动或撤销行程归属；系统以期望当前 Link 防止覆盖并发决定；
5. 历史归属不被原地改写，删除 Fact 只终止活动 Link。模型不自动接受建议，归属不改变金额分配或正式字段。

## M3 报销工作流旅程

1. Owner/Finance 选择一个 Trip，并从当前活动归属中显式勾选本次报销包含的 Payment/Invoice；系统不默认全选、不改变原 Fact 或 Link；
2. 本地 `reimbursement-policy/1` 对当前选择给出缺少发票、选中 Link 金额未覆盖 Fact 总额和同一 Fact 已在其他有效报销中的确定性提示，并按币种分别汇总；
3. 用户查看完整提示、显式确认当前全部 Finding 并填写理由；服务端在事务内重算快照，变化时保留草稿并要求刷新，不自动忽略提示；
4. 成功后系统保存不可变 Trip/Assignment/Fact 快照、Finding、提交决定与 AuditEvent，当前状态为“已提交”；
5. Owner/Finance 以期望状态和版本把记录标记为“已报销”或“已驳回”，也可带理由重新打开；每次变化追加历史，不覆盖旧决定。Viewer 只读，Reviewer 不可枚举。

## M4 数据洞察与查询旅程

1. Owner、Finance 或 Viewer 进入“数据洞察”，系统默认读取全部当前未删除 Payment/Invoice，不调用模型，也不建立统计副本；
2. 用户可按 Fact 类型、完整起止日期、币种、分配状态和行程归属筛选；指定 Trip 时必须显式选择“已归属”，不存在或跨租户 Trip 不泄露；
3. 系统按币种和 Fact 类型分别展示数量、总额、已分配、剩余及三种分配状态数量，禁止生成 Payment/Invoice 合并总额或跨币种总额；
4. 明细使用稳定不透明游标加载更多，逐项展示业务日期、摘要、整数金额、分配状态和当前行程；Payment 日期只读取确认时持久化的 `business_date`；
5. 汇总与本页明细来自同一 PostgreSQL `REPEATABLE READ` 只读快照。筛选、活动 Link 或归属发生变化时，新请求重新读取当前 Fact，不把旧结果当作第二数据源。

## 产品成功的判断

产品成功不是“模型调用成功”，而是：

- 用户能够发现并修正错误结果；
- 无效 AI 输出不能污染正式数据；
- 重复操作不会生成重复事实；
- 正式数据可追溯且跨租户不可见；
- 新用户可以通过一个 Compose 流程完成全新部署并真实走通首条链路。
